## 0. Headline answers

1. OBSERVED: **there is no server-to-client snapshot over any network layer in this exe.** `Netchan_Transmit` (rva 0x203200) has exactly two callers: 0xcd340 (client -> server, usercmds of a local client)
   and 0x22f400 (host's coop frame sender, which skips loopback slots). `NET_SendPacket` wrapper 0x200b60 is called only from Netchan_Transmit, Netchan_TransmitNextFragment (0x203300) and the two
   out-of-band senders (0x202c30, 0x202cf0). There are no `getchallenge`, `connectResponse`, `gamestate`, `CL_ParseServerMessage` strings (strsub search); the strings `svc_snapshot` / `svc_EOF` (rva 0x3308e0 / 0x3308f0)
   sit in an unrelated pointer table (rva 0x3be9f0) with no code reference. The SP server and client live in one process and the server hands the data over by **direct function calls and shared globals**
   (section 2). This holds on the host and on the partner PC alike (each runs the whole simulation; only the usercmd "coop frames" cross the wire).
2. OBSERVED: the hand-over function `snapshot publish` (rva 0x234540) is written for more than one local client: it loops over BOTH coop slots, and for every slot whose address type is 2 (loopback = "local") it copies that slot's
   server playerState (0xaca4 bytes) into `cl[localClientNum].ps`. The local client number is the 16-bit field at slot+0x18 (the "port" of the slot's address). In the current coop only slot 0 (host) or slot 1 (partner PC) is type 2.
3. OBSERVED: the consumer side (arrays indexed by local client number in the code: `cls` stride 0x10 at rva 0x533cb0, `cl` stride 0xce9c at rva 0x533cc0, `cl2` stride 0x3218 at rva 0x545840) exists in memory ONCE.
   `cl[1].ps` would be rva 0x542bd4 = inside the coop slot table (rva 0x540ba0..0x545840). So a second local client needs private storage for these (hook or swap) but NOT a second socket/netchan for snapshots.
4. OBSERVED: the cgame renders the first-person view of whichever game client's playerState sits in `cl[lc].ps`; `cg.clientNum` (rva 0x40caa0) is copied from `ps+0x100` of that state when the cgame is initialised (rva 0xb8830).
   Which game client lands in `cl[lc]` is decided by the slot table in 0x234540: slot s with type 2 -> game client s's ps -> `cl[slot[s].+0x18]`. On the partner PC (local slot = 1, +0x18 = 0) the view is game client 1.
5. INFERRED consequence for the plan: phase 1 ("second client over a second socket, each receives snapshots") is not needed for snapshots. What is needed is a second *local slot* (type 2, +0x18 = 1) plus private storage for the client side. The usercmd direction (0xcd340 always sends through slot 0's netchan at rva 0x540ba0) is a separate problem (other agents).

## 2. What the server hands the client (OBSERVED)

### 2.1 rva 0x234540 `snapshot publish` (no args; only caller 0x2349a0)
Reads: coop flag DAT 0x52fb5c; DAT 0x3c3eb0 (player count; initial value 1; WRITTEN by 0x171370, 0x22d460 (partner accept), 0x22d830 (host accept)); DAT 0x19b48c0 (server state: 0 off, 2 running); game entity base ptr DAT 0x19c3848 (stride 0x2a0, count DAT 0x19c3850); slot table (rva 0x540bb0 = slot[0].type, stride 0x2650).
Writes:
* **entity list**: `DAT 0x19c38cc` (count) + `DAT 0x19c38d0[]` (ushort entity numbers). Entity n is listed if `gentity[n]+0xac != 0` and `(gentity[n]+0xae & 1) == 0` (only when DAT 0x19b48c0 != 0). **Entities 0 and 1 are left OUT when their slot is local** (coop: `slot[n].type == 2`; non-coop: `n < DAT 0x3c3eb0`). So a local player's own entity never appears in the list; a remote partner's entity does.
* **second list**: `DAT 0x19c48d0` (count) + `DAT 0x19c48d4[]`: indices (max 0x300) of records at rva 0xcdb1e0 + n*0x24 whose byte at +0x21 has bit 0x10; their 0x24-byte bodies are mirrored to rva 0x1a1c410 + n*0x24. Meaning: unknown (client-visible scripted objects?).
* **entity states**: `rva 0x19c6410 + n*0xac` = first 0xac bytes of gentity n (entityState_t) for every listed n; **plus** for every i in [0, DAT 0x3c3eb0) the state of entity i (the players) regardless of listing. Accessor `0x234520(n)` returns `0x19c6410 + n*0xac`.
* **playerState per local slot**: for slot i in 0..1 (coop: type 2; non-coop: i < DAT 0x3c3eb0): `0xd5690(i, 0x2316c0(i))`. `0x2316c0(i) = i * DAT 0x19c3860 + DAT 0x19c3858` = game client i's playerState (client array base/stride).
* **header message** (built in a local 0x4000 buffer, never sent): byte 0, long `0x171360()` (= level.time, DAT 0xd96ec8), byte DAT 0x19ada90, then `0x14016aa20(msg, 0x171350())` (a delta list of script/game "data table" entries from DAT 0xcf75a8: 11-bit index, 2-bit type, payload; 0x400 = end), byte 1 (end). `DAT 0x19b07ac++` (snapshot counter, reset to 1 in 0x22d040). Then `0xd3ee0(msg)` -> `0xd5610(msg)` parses it locally: `DAT 0x548cec = ReadLong` (snapshot serverTime), `DAT 0x548ce8 = ReadByte` (flags), `0xa1e20(msg)` reads the delta list into the global table rva 0x3fef51 (0x400 entries x 5 bytes). This part is shared by all local clients (global), not per client.

### 2.2 rva 0x2349a0 `publish server commands then snapshot` (callers 0x2343a0, 0x230f50)
`0x174e50(); for i in 0..DAT 0x3c3eb0 (coop: if slot[i].type == 2; lc = slot[i].+0x18): 0xd5470(lc, &DAT 0x19ada9c + i*0x1678); after each: client_t[i].+0xc = client_t[i].+8 (ack = seq), client_t[i].+4 = 0 (length); then 0x234540()`.
Server commands are queued by `0x232c30(client_t*, text)` ONLY for local clients (same type-2 test); `0x233bf0(client_t*|NULL, fmt, ...)` broadcasts to all `client_t` with state 4 (< DAT 0x3c3eb0); config-string changes (0x232450) send `"cs %i %s"` this way.

### 2.3 Server client array: rva 0x19ada98, stride 0x1678, exactly 2 entries (`0x22d040` memsets 0x2cf0)
`+0` state (4 = active), `+4` reliable command buffer {len, seq(+8), ack(+0xc), text(+0x10, 0x1000 bytes), offsets table (+0x1010, 128 ints)}, `+0x1210` nonzero = coop peer in use (4 for the local and for an arrived partner), `+0x162c` last packet time, `+0x1630` last-frame level.time, `+0x1670` pointer to the gentity. `0x22d040` (map start): for each slot used (coop: type != 0; non-coop: i < DAT 0x3c3eb0): `client_t[i].state = 4`, and if `i < DAT 0x1919314` also `+0x1210 = 4` and name "player %i". The array at rva 0x3cf180 stride 0xe80 (4 entries) is NOT this: it is a cgame per-local-client array (users 0x6a1c0 [called from 0xb87b0], 0x6a570, 0x699c0, 0x69260, 0x693e0, 0x68b70, 0x68d60, 0x685c0).

## 3. Client-side receive path and the state it feeds (OBSERVED)

No netchan is read for snapshots. The only loopback-ring reads: `NET_GetLoopPacket` 0x202a60 is reached through 0x202a30 (callers 0x1fbb80, 0x1fd7c0, both with first argument 1 = the server's ring) and through the pump 0x200840 (rings of sock 1 and sock 0 are drained into a 0x200-entry delay queue at rva 0x1385570, stride 0x60, ring 0x1391690/0x14118a0 as in the plan). Nobody asks `0x202a30` for socket 0, and nothing sends to a loopback client ring (0x22f400 skips type 2), so the sock-0 loopback ring carries nothing.
Partner side of the lockstep: host frames arrive on UDP into `0x1fbb80 -> 0x230020 -> Netchan_Process(0x202ff0, slot netchan) -> opcode 0x1d, subtype 1 -> 0x22edd0` which pushes them into a 20-entry ring (rva 0x192d388, stride 0x38, head DAT 0x1919378, tail DAT 0x191937c) consumed by the stepper; subtype 0 (partner usercmds) -> 0x22f0d0 on the host (`DAT 0x1905302` = 1 on the host, 0 on the partner). These are "coop frames", not snapshots.

Client snapshot state (all single statics):

## 4. Which player's view the cgame renders (3)

OBSERVED chain: slot table -> `0x234540` picks the playerState -> `cl[lc].ps` -> `0xca270(lc)` -> `0xb8000` (ping-pong buffer) -> `0xb28b0` / `0xb8a20` copy into `cg.ps` (rva 0x422440). So "whose view" = **the ps in cl[lc].ps**, i.e. `ps.clientNum` (+0x100). There is no separate `cl.clientNum`.
* `cg.clientNum` (DAT 0x40caa0) is written ONLY by `0xb8830` (cgame init for lc, from `nextPs+0x100`); it is used to recognise the player's own entity: `0x9c810` walks the snapshot entity list and treats an entity with eType 8 whose clientNum (cg_entities +0x160) equals `cg.clientNum` as "self" (returns it so the first-person model/shadow is handled), other players are drawn normally.
* `0xbca00` / `0xb28b0` / `0x6b230` / `0xa5ec0` map `lc -> slot index` by scanning the slot table for `type == 2 && ushort(+0x18) == lc` (default 0). Some arrays are indexed by SLOT index (e.g. `rva 0x3d1b38 + slot*0x210c` via 0x6b230), others by lc (`rva 0x3cf180 + lc*0xe80`, `rva 0x51e364 + lc*0x2cd0`, `rva 0x52c6c0 + lc*0x54`).
* The own entity is fed through the ps path: 0xb90d0 refreshes `cg_entities[ps.clientNum]` from `0x234520(ps.clientNum)`, which is why 0x234540 copies the local players' states although their entities are unlisted.
* Partner PC: slot 1 type 2 with +0x18 = 0 -> game client 1's ps lands in cl[0]; `ps.clientNum == 1`; entity 0 (the host) is listed and drawn as a world entity. That is what the mod observes (partner sees the host's model).
* What makes a second context show player 1: its own `cl[1].ps` = game client 1's ps (publisher does this when slot 1 is type 2, +0x18 = 1), its own `cg.nextPs/prevPs/ps`, its own `cg.clientNum`, and entity 0 present in the entity list (the stock publisher omits both local players).

## 5. Connection / first steps of a client (4)

* There is no challenge/gamestate exchange for the local client (see 0). OOB messages of the coop session (strings): `coopConnect` (partner -> host, written by 0xd23c0: string `coopConnect`, byte 0x1d protocol, 8-byte player id, player name string, byte (value of a dvar at DAT 0x1a2f7b8)), `coopAccept` (host -> partner; slot number, player count DAT 0x3c3eb0, map name, time DAT 0x1419ada44, skill, party data), `coopAcceptAck`, `coopReject COOP_WRONGPROTOCOL|COOP_FULL|COOP_WRONGSTATE`, `coopLaunch`, `coopLoaded`, `coopDis`, `coopRestart`.
* Host own player (0xd25e0 `listen`, run when `cls.state[0] < 3`): clears slot types, `slot0.type = 2`, `slot0.+0x18 = 0` (DAT 0x540bb8), `Netchan_Setup(sock 0, slot0, {type 2, 127.0.0.1, port 0}, 0, bufs 0x5411d8/0x5421d8 x 0x1000)` (rva 0x203190; the netchan struct is 0x638 bytes: +0 outSeq, +4 sock, +0x10 address (type, ip, port at +0x18), +0x30/+0x38 fragment buffer, +0x48/+0x50 send buffer), `DAT 0x14052fb5c = 1`, `DAT 0x1919314 = 1`, `DAT 0x1905302 = 1`, party member for lc 0 (`0xd7220(0, ...)`, 0xd7c70, 0xd7b30), UI state 0xb ("coop_lobby") via `0x24ee50(0, 0xb)`.
* **0x24ee50 is NOT the cls state**: it sets the UI/menu state `DAT 0x141a49dc4[lc]` (0 in game, 2 pause, 3 pregame, 4 end, 6 briefing, 7 victory, 0xa savegameloading, 0xb coop_lobby, 0xc levels_challenge, 0xd main_text, 0xe main_specops).
* Partner connect (0xd23c0): sets up `slot0` toward the host (sock 0), `DAT 0x1905301 = 1`, sends `coopConnect`. On `coopAccept` the partner's 0x22d460 does `slot[assigned].type = 2`, `slot[assigned].+0x18 = lc (0)`, `Netchan_Setup(1, slot0, host address, ...)`, `DAT 0x3c3eb0 = count`, `DAT 0x1905302 = 0`, party members, and answers `coopAcceptAck`.
* **cls state**, `DAT 0x533cb8 + lc*0x10` (so lc 1 = 0x533cc8, which is INSIDE cl[0], at cl+8): OBSERVED writes: 0 = idle/disconnected (0xd28e0, 0xd3190, 0xd46c0, 0xca9e0); 1 = "map" command accepted (0xca8f0); 4 = loading (0xd3f10, 0xd2870); 7 = loaded, waiting (0xd2870 when DAT 0x5dac53, 0xd31f0); **6 = active (0xca600)**. Values 2, 3, 5: no direct writer found (0xd46c0 and 0xd2940 reset 2 to 0; 5 has no case in the 0xd5890 switch). 0xd5890 draws the cgame only for state 6; 0xcd340 sends usercmds only for state >= 3 and `DAT 0x13260e8 == 0`.
* **0xca600** already contains the second-local-client case: coop: `if (slot0.type == 2) cls.state[slot0.+0x18] = 6; if (slot1.type == 2) cls.state[slot1.+0x18] = 6` (slot1's field read from DAT 0x543208); non-coop: `if (DAT 0x3c3eb0 > 1) DAT 0x533cc8 = 6`. With +0x18 = 1 this write lands in cl[0]+8 (corruption unless redirected). Callers: 0x22c970, 0x2326a0.
* What a second local client would have to do (INFERRED from the host's own sequence): slot 1 = type 2, +0x18 = 1 (+ `Netchan_Setup` only if its usercmd packets go through a netchan); party member lc 1 (0xd7220 with local flag 1, then 0xd7c70(1,..), 0xd7b30(1,..) as 0x22d460 does); at map load the engine already loops over all local slots (0x2326a0 -> 0x24afc0(lc); 0xca0f0 -> 0xb8830(lc), 0xb87b0(lc); 0xca600); no OOB handshake, no challenge.

## 7. What a second local client needs from this part (plain words)

* Can a second LOCAL client get its own snapshot? **Yes, and the server already knows how.** A "snapshot" here is not a network message: it is (a) a per-local-client playerState copied into `cl[lc].ps`, (b) a per-local-client server-command batch, and (c) shared tables (entity list, entity states, the delta data table). The publisher (0x234540 / 0x2349a0) does (a) and (b) for every slot that is "local" (type 2). Make slot 1 local (type 2, +0x18 = 1; or the non-coop route `DAT 0x52fb5c == 0` with `DAT 0x3c3eb0 == 2`, the original console split-screen route, untested here) and game client 1's ps and commands are published under lc = 1.
* No second socket, challenge or gamestate is needed for this part. The snapshot never touches a netchan. (The usercmd direction does: `0xcd340` always uses slot 0's netchan, and the host tells clients apart by source address / loopback port. Not examined here.)
* Missing: memory. `cl[1]` (ps at 0x542bd4), `cl2[1]`, `cls[1]` (0x533cc8) point into other data. Three tiny functions need redirecting for lc >= 1, or the lc-0 slots swapped per context: `0xd5690` (ps in), `0xd5470` (commands in), `0xca270` (ps out; also returns the command sequence), plus `0xc97e0` (command execution) and the cls writes of `0xca600` / `0xd3190` / `0xd28e0`.
* Missing: a cgame per context. Everything the consumer touches is a single static (section 3 and the "Direct global use" list): `cl.snap` pointers and 2 snapshot buffers (0x51b070-0x51c698), cg_entities (0x441070, 0xd0000 bytes), the object table (0x521040, 0x300 x 0x38), bitsets (0x52c300/0x52c400), cgame ps buffers + pointers + `cg.clientNum` (0x40caa0-0x42242c), `cg` (0x422428 onwards, ps at 0x422440), per-player records (0x51dcc4/0x51dd54), the per-lc arrays in section 6. Consume with the swapped context in the same order as the stock code: `0xb8300` (once), `0xb8000(lc)`, `0xb9320`, `0xb8ad0`, later `0xbc170` (-> `0xb8c50` -> `0xb90d0`, `0xb8a20`; `0xb28b0`), `0xbca00`. At map load the first-snapshot calls `0xb8830(lc)` and `0xb87b0(lc)`.
* Timing: the publish happens once per finished 50 ms server frame, inside the client frame (0xd5890 -> 0xbc1a0 -> 0xb8d30 -> 0x2343a0). Publish ONCE, then consume per context right after (the consumer reads the shared globals, which are overwritten at the next publish). One client frame = at most one new snapshot; the server frame rate (20/s) is below the 30-60 fps client frame rate, so a frame often has no new snapshot (the cgame then only interpolates with `DAT 0x51dcb0`).
* The stock publisher leaves BOTH local players' entities out of the entity list (they are fed through the ps path). With two local views each player must see the other one's entity: patch/hook the two `slot.type == 2` skip tests in 0x234540 (or append entities 0 and 1 to `DAT 0x19c38d0` after it) and rely on `cg.clientNum` to recognise "self" (0x9c810). INFERRED: the entity states for players 0..`DAT 0x3c3eb0`-1 are already copied to `0x19c6410`.
* Shared and safe to keep single: the game/server simulation, `DAT 0x19c38d0` list, `0x19c6410` entity states, the delta data table (0x3fef51), config strings (0x19b58f2 / client cache 0x5d8d02), server time globals, level.time.
* Open (unknown): meaning of the second list (0xcdb1e0 records); whether cg_entities could be shared between contexts (0xb90d0 does per-ps-client work); behaviour of the coop wait/ack logic (0x22e470, 0x22e7a0, 0x22ed70, 0x22e120) when both slots are type 2 (they read the slot types and `DAT 0x1905302`); how client 1's usercmds enter the lockstep frame ring when its slot is local; the writers of cls state 2/3/5; whether the non-coop 2-player route runs at all on the PC build (`IsSplitScreen()` builtin rva 0x194720 calls 0x222140(0), and 0x70240/0x70230 are stubs returning 0).
