# Code audit, 2026-10-25

Scope: the DLL (`src/*.c`, 7600 lines), the GSC modules (`content/scripts/maps/_mw2coop*.gsc`) and the
patch generators (`tools/gen_*.py`). Method: a read of the code that touches resources (allocation,
handles, sockets, threads, loops, string buffers, the network packets), greps for every allocation and
every unbounded copy, per-function scans of the GSC modules for entities and HUD elements that are spawned
and never deleted, loops without `endon`, and a count of what a session writes to the log. Nothing was
profiled with a tool: the performance remarks are from reading, not from a measurement. Nothing here was
changed by the audit; each item says what a fix would be.

Severity: **M** medium (a real, reachable problem), **L** low (small, or needs unusual conditions),
**N** note (not a bug: a design choice or a cleanup).

## Status after the review (2026-10-25)

## DLL

### M1. The host's start packet and the lobby's "ready" packet are accepted from any sender
`net.c:210` hands every incoming `0xffffffff`-prefixed packet to `progress_on_packet(buf, len)`
(`progress.c:496`) and `menus_on_packet(buf, len)` (`menus.c:933`). Neither function is given the sender's
address, so a UDP packet from anybody to the game's port that starts with `mw2coop_start` or `mw2coop_ready`
is acted on:
- `mw2coop_start` sets the session dvars the host sends (`start`, `mw2coop_god`, `mw2coop_ff`,
  `mw2coop_cp_start`, `mw2coop_cp_pos`) and the difficulty (`skill_apply`).
- `mw2coop_ready` sets the partner's id, Steam ID and ready state shown in the lobby.

The values are checked (a fixed list of dvar names, identifier characters only, one digit for the skill,
`sscanf` with `%32s` into 33 bytes), so this is not a memory-safety problem. It is a spoofing problem: a
stranger who knows the port can change the start point or difficulty of a session that is being set up,
or show a false "partner ready" (and a false partner id, which the save-member check reads).
Fix: `my_recvfrom` already knows `from` and `remember_peer()` already stores the partner's address. Accept
these two packets only from the stored peer (the host's address on the client; the client's on the host), and
`access_on_packet`-style lobby packets as they are.

### M2. The command file interface is on in released builds
`control.c:350` starts a thread that, every 250 ms, opens `mw2coop\commands.txt` and runs every line as a
console command (`game_cbuf_addtext`). It is the QA harness (the whole of `tools/qa_pair.sh` rests on it), and
it also runs in the build players get. Anything that can write a file in the game folder can run console
commands (`quit`, `map`, `exec`, `set`). Same user, same folder: not a privilege escalation, but a standing
door a player does not know about. It also costs a `CreateFile` four times a second for the whole session.
Fix: start the thread only when the file exists at start-up, or when a dvar/INI setting (`qa=1`) is on, and say
so in the README.

### M3. Log file grows without bound
`log.c:23` opens `mw2coop.log` with `FILE_APPEND_DATA` and nothing ever truncates or rotates it. The session
recorder (`_mw2coop_rec.gsc`) writes one position line per player every second (about 90 bytes each, measured on
a QA log) plus the allies every five seconds and the events, so an hour of play is roughly 0.8-1 MB; a player who
never deletes the file ends with tens of megabytes that they are asked to send for bug reports. Fix: when the file is larger than a few MB at start-up, rename it to `mw2coop.log.old` (replacing the
previous one).

### L1. `transplant_clone` leaks the old model's buffers when it makes a clone again
`transplant.c:351`: "the same name in a new level: made again". The second `put_surfaces` calls `calloc` /
`malloc` for the surfaces, blend data, lists and the surface copy (`transplant.c:213-250`, `436-463`) and
overwrites the pool entry; the first set is never freed (there is no `free` in the file). The same for the
two small `malloc`s of the upright ice pick (`transplant.c:417-421`) when its source model moves between
levels. A few hundred KB per level load, which matters for a QA run that restarts a level dozens of times and
not for a normal session. Fix: keep the pointers of the last clone in `clones[i]` and free them before the next
`put_surfaces` (careful: only once the pool entry no longer points at them).

### L2. Path buffers are extended with `lstrcatA` after `GetModuleFileNameA`
`control.c:445`, `crash.c:153-154`, `log.c:17`, `progress.c:541`, `scripts.c:379`, `settings.c:97`,
`shot.c:148`. Each takes `MAX_PATH`, cuts the file name off and appends 10-20 characters. With an install path
longer than about 240 characters the append overruns the buffer; `GetModuleFileNameA` also leaves the buffer
unterminated when the path is truncated. Windows paths that long are rare, and the Steam folders the game is
installed in are short. Fix: one helper `mod_path(buf, size, "name")` using `snprintf` and an explicit check of
the `GetModuleFileNameA` result, replacing the seven copies.

### L3. Hooks are written into running code while the game's threads run
All hooks (`scripts.c`, `localize.c`, `zones.c`, `scrdebug.c`, `transplant.c`, `steamnet.c`) copy a 14-byte
`jmp [rip+0]` over game code with `memcpy` after `VirtualProtect`, from the watcher thread once the game
window exists (`main.c:watcher`). The copy is not atomic; a game thread that executes those bytes in that
instant would crash. None of the patched functions is hot at that moment (script loading, zone loading, a
Steam join), and none has crashed in the QA logs, so the risk is theoretical. Fix, if wanted: suspend the
other threads for the few microseconds (the crash module already enumerates them).

### L4. `fov.c` wakes 100 times a second for the whole session
`fov.c:20`: `Sleep(10)` in a loop that reads two dvars and does nothing unless the Predator's field of view
is on. The cost is tiny (a few dvar lookups) but it never stops, on both machines. Fix: sleep 10 ms only while
`mw2coop_fov_pilot` is "1" or "2", 100 ms otherwise (the first frame of the Predator view then may show the
wrong field of view for up to a tenth of a second: check on the real thing before taking this).

### N1. Four copies of the same trampoline code, and the trampolines are RWX pages
`localize.c:296`, `zones.c:130`, `scrdebug.c:208`, `transplant.c:550` each allocate 64 bytes with
`PAGE_EXECUTE_READWRITE`, copy the original bytes, append a `jmp`, and keep the page writable and executable for
the rest of the process. One helper `hook_install(target, expected_bytes, replacement, &original)` would remove
about 80 duplicated lines, and could write the trampoline into a read-write page and then switch it to
`PAGE_EXECUTE_READ`. The second part also matters for antivirus heuristics (RWX allocations are one of the things
they score; the Nexus quarantine of 0.4.7 is already in the notes), so it is worth doing when the owner allows a
DLL change for that reason.

### N2. `malloc` and `HeapAlloc` results are not checked
`scripts.c`, `scrdebug.c`, `transplant.c`, `menus.c`. An out-of-memory process would crash on the next line
instead of the game's own crash. At the sizes involved this does not happen; a one-line `xmalloc` that logs and
exits would make it explicit.

### N3. `scrdebug` parses every loaded script at every level load
`scrdebug.c:66` tokenises the whole text of each script that is loaded, always, to be able to name functions in
script errors. It costs milliseconds at load time (not during play) and allocates the function-name tables
once per file (they are freed and rebuilt on reload, `scrdebug.c:85`; no leak). Could be switched off by a
setting for released builds, since only the logs of players who report errors use it.

### Checked and fine
- Menus (`menus.c`): the `HeapAlloc`s that are never freed (`ui_script_set`, `ui_clone_*`, `menus.c:159-245`,
  `1104`) run once per process: the log of a QA run that restarted the level five times shows the "co-op buttons
  added" lines once.
- Sockets (`upnp.c`): every `socket()` is closed on each path; `getaddrinfo` results are freed. The return value
  of `socket()` is not checked against `INVALID_SOCKET` (the following calls then fail harmlessly), and a router
  without UPnP is searched once per run, not every few seconds (`upnp.c:289`).
- `scripts.c` patch application: the buffer arithmetic of `subst_in_function` and the `replace`/`append` paths was
  walked through; every `malloc` has its `free` on every path including the malformed-patch `break`.
- `net.c`: the packet logger is capped (150 packets per run), `contains()` and the per-packet checks are cheap,
  the broadcast function frees its adapter list.
- `steamnet.c`: the 2 KB packet buffer is static and checked against the caller's length; only accepted Steam
  friends can open a session.
- `mirror.c`: wraps five script methods; the extra work (two dvar lookups) runs only when player 1 calls them in
  co-op, a few times per level.

## GSC modules

- No entity or HUD leak of consequence. A scan of every function that spawns an entity or HUD element and does not
  delete it found 23; the ones that matter are the ones that can run more than once in a level
  (`player_tag_ent`, `lane_ent`, `black_overlay`), and all of them cache or are called once. The rest are scene
  entities that live until the level ends, where the engine frees them.
- Forever loops: 30 `for ( ;; )` loops, ten without `endon`. Each either ends on its own condition (the leap and
  boarding waits), is a 0.25 s poll (`snowmobile_looks`) or is the QA god mode. The always-on level watchers poll at
  0.05 s (player 2 following player 1) and 0.25 s (the weapon sync), a few operations each.
- Not a leak, but a cost to know about: the weapon sync (`_mw2coop.gsc:606`) builds two weapon arrays four times a
  second for the whole level.
- The checks that were wrong during this work, for the record (all fixed): `GetEntArray(flag, "script_flag")` finds
  nothing in this engine; a module must not define a function that an included `_utility` also defines
  (`open_up_fov`: "function already defined" stops every script of the level); a patch `replace` hunk needs a final
  newline in both texts or the patch is malformed (`check_patches.py` says so, but `deploy.sh` still copies it).

## Patch generators

- `deploy.sh` prints "1 PROBLEM(S)" from `check_patches.py` and goes on to copy the broken patch. It should stop.
- `tools/gen_seek_patches.py` has grown special cases for four levels (Cliffhanger, favela_escape's ladder and
  big jump, af_caves). They work, but each is a long block in a script named for "seek" patches; moving them to
  `gen_favela_escape_patches.py` and a new `gen_af_caves_patches.py` would keep the generators one per level, as
  the others are.
