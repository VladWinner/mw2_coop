# Changelog

## Unreleased

- **64-bit: the code's addresses go through the address resolver too, and a 64-bit build whose addresses moved can be tried (`[native] movedbuilds=1`, experimental).** The 64-bit code wrote its game addresses inline (`base + 0x...`, about 450 places); they are `base + XR(0x...)` now, `XR()` is the resolver in 64-bit as in 32-bit (the same number on the known build), `addresses-x64.txt` lists 295 addresses instead of 120, and an unknown 64-bit exe whose addresses were found (85% or more) runs only when you switch `movedbuilds` on. Checked: the 64-bit DLL's code and data were byte-identical before `XR()` became the resolver, and the resolver finds 281 of the 295 addresses on the reference exe, every one itself (the Python and the C resolver agree). Not checked: a build that actually moved (none exists to try). Also fixed: the `movedbuilds` setting was never read from `settings.ini` (a path typo), only the `MW2COOP_MOVED` variable worked.
- **settings.ini is made by the game at launch and kept up to date.** The release archive no longer carries a `settings.ini`: the mod makes `mw2coop\settings.ini` from its built-in, documented defaults the first time the game starts, and at every start brings an existing one up to date with this version (new keys and comments come in, in the template's order) while keeping what you changed: a value, a commented default you switched on, and keys and sections the template does not know (the console writes some, tests and newer versions use others). Comments you wrote yourself are not kept; the file as it was goes to `settings.ini.bak` whenever the merge changes it. A file that is not UTF-8/ANSI text (UTF-16) or not writable is left alone. An update of the mod can no longer overwrite your settings. The merge is `src/inimerge.c` (checked by `tools/test_inimerge.sh`, which also runs the on-disk part, `src/inisync.c`); the template is `content/release/settings.ini`, built into the DLL by `tools/gen_settings_template.py`.
- **32-bit: more of the code goes through the address resolver, and the level start is logged.** The name table guard (`guards.c`), the ADS-on-climb fix (`climbads.c`) and the settings menu's UI struct (`gfxopts.c`) read their addresses through `XR()` now, so a game build whose addresses moved gets them from the signature file (eight new entries in `addresses-x86.txt`, all checked to resolve to themselves on the official image) instead of reading the official ones. New log-only hooks at the level start (`svlog:` lines: `ClientBegin`, the per-client init, the server client connect, with the entity's sentient pointer and the co-op state) to find out why the 32-bit co-op client can crash in `ClientSpawn` when player 2 has no sentient (see the crash analysis in the notes); they change nothing.
- **One 32-bit DLL for the official 32-bit game and the iw4x-sp client; the separate iw4x archive is gone.** The mod used to be built in three profiles (64-bit, 32-bit, 32-bit for iw4x-sp 1.0.159 with its own addresses compiled in). The iw4x profile is merged into the 32-bit one: the DLL looks at the process at start (the exe name `iw4x-sp.exe`, then the SHA-256 of `iw4sp.exe`), and for the 1.0.159 exe it uses the address table `src/addr159.c` (about 300 official-to-iw4x pairs, generated by `tools/gen_addr159.py`); the iw4x-only code paths (connect with a plain port, the name watermark, diagnostics) run only there. So there are two archives per release now, 64-bit and 32-bit (`-x86`), and iw4x-sp players use the 32-bit one (see its `INSTALL.txt`). Checked on the iw4x-sp client with the merged DLL: split screen on, 0 refused hooks, 0 CRASH; and on the official 32-bit build.
- **Split screen in Special Ops (not only the campaign).** Special Ops' menu (`main_specops`) gets a "Split screen" button under "Two players online". It opens Spec Ops' own lobby with the second player on this PC: the op list (Change Op) and the difficulty row are the game's, the two device cards and the Start button are the split screen's (each player presses a button on his device, then Start), and the op starts as a native split screen level with Spec Ops' own loading screen (`specialops` is left at 1; the campaign's look is only for campaign missions). After the op the split screen returns to the lobby, as it does after a campaign mission. Nothing of the campaign's menu changes (title, mission picture, music, leave routing) in such a lobby. The scripts of an op are the game's: `is_campaign_coop()` is false on `so_` maps, so the mod's co-op GSC does only what it does for any Spec Ops session.
- **Ultrawide: the menus keep their 16:9 margins (`[display] safearea_auto`, on by default).**
- **Single player runs the game's own scripts: none of the mod's GSC is loaded.** The campaign or a Spec Ops mission played alone (the dvar `coop` is not 1) no longer gets the mod's scripts (`maps\_mw2coop*`) or any of its patches of the game's scripts; they were guarded for one player, but every guard was one more place where single player could differ from the shipped game (the recent Cliffhanger fixes were of this kind). The dvar is read at every script load, so a session of one after a session of two, and the other way round, gets the right text (the 32-bit iw4x loader keeps its cache for co-op sessions only). The Discord card no longer shows a stale "Co-op" in single player. The exception is the fixes of the game's own bugs that have nothing to do with a second player: they are files of their own, `<script>.fix.patch` and `maps\_mw2fix*.gsc`, and load in every session. The first is the Museum civilians' fix (a stripped assert, T-pose civilians and script errors, in single player too), moved out of the co-op patch for it; every other patch and script of the mod is about the co-op and stays out of single player.
- **A build whose addresses moved: the 32-bit mod can now try it (opt-in, experimental).** With `[native] movedbuilds=1` in `mw2coop/settings.ini` (or `MW2COOP_MOVED=1` for QA), an `iw4sp.exe` that is not the known one and has other addresses is no longer left alone when the signatures find at least 85% of the mod's addresses: the mod runs with what it found. The 32-bit code reads its addresses through `addr_xr()` now (the `RVA_` macros of the official block and `XR()` / `XV()`; the same numbers as before on a known build). An address that was not found points at a harmless block of memory (a code block that is all `ret`, a data block of zeros) instead of the exe's own header, so a feature without its addresses does nothing and nothing else is touched; the reference build's code ranges are in the signature files (`# code` lines) to tell the two apart. The script-builtin table entries the mod wraps (the player-method mirror, `setdvar`, `visionsetnaked`) are found by their names when they are not where the known build had them (`game_builtin_entry`), and a hook site that is not readable is refused instead of faulted on. Tried on the iw4x-sp client's 1.0.159 exe (213 of 241 addresses found): the mod started and ran through its installs without a crash, and most hooks were refused because that exe's code differs from the official one (the iw4x profile build is the way for that exe). Checked after the change on the official 32-bit build (the split screen starts as before); not re-checked: the 64-bit build, which shares the changed files. See `docs/address-resolution.md`.
- **Two split-screen crashes from Vlad's log (2026-11-09) and the Multiplayer button.** (1) A crash on the render thread at the end of the Museum load (2560 x 1080 screen): the 'layer' pass of the split screen called the saved original `SetRenderTarget` / `SetViewport` through a pointer that was still null (the 16:9 cinematics hooks put the draw hook in before the full device hooks are in); the layer helpers now do nothing until the originals are known. Found by building the nightly commit with symbols and reading the crash address (`native.c layer_to_scene`). (2) A crash when the second player bled out: the developer console, rebuilding its completion list, walked the game's command list and compared the name of a node that had been freed under it; the walk now checks each node and each name before using it (`game.c game_for_each_command` / `game_for_each_dvar`). The checks use `VirtualQuery`, not `IsBadReadPtr`: the caught faults of the latter are written to the log as CRASH lines, and the crash logger keeps only the first three. The crash logger also no longer counts a fault inside kernel32 / kernelbase (the caught probe of `IsBadReadPtr` and the like), so those cannot use up its three entries. Neither crash was reproduced here: the guards are checked to build and to leave a normal split-screen run as it was. The main menu's **Multiplayer** button now runs the game's own Multiplayer action (the one of the game's own selection menu); the mod's modes (Co-op, Split screen) are on the Campaign page only, and the mod's own Multiplayer popup is gone.

The Campaign page gets **Co-op** (two players online) and **Split screen** under Mission Select. The icons are a picture of their own (`mw2coop/about-icons.tga`) on a copy of the logo's material, so nothing the game draws elsewhere changes. Checked in the game (64-bit and 32-bit, 1920 x 1080): the main menu, the Campaign page (64-bit) and the About page; not checked: clicking the icons, other resolutions. The About text has a shadow for readability over the picture (a dark box behind it did not draw, so there is none).

The logo moved to the top of the left panel with "ENHANCED" under it, and the dark panel and the line in it fade out to the right instead of ending in a hard edge. The entries are in `mw2coop/menus.menu` (`.menu` syntax: the three top entries, the Multiplayer popup, and now the yes/no questions of the host's menu too); the new texts (MULTIPLAYER, SETTINGS, the subtitle) are in `mw2coop.str`. The game's "Main menu" button and its Campaign / Spec Ops chooser are not used any more (the Spec Ops page's Main menu button now leads to the mod's list; Esc closes the Spec Ops, Campaign and About pages; the first entry has the focus when the main menu opens, so a key or a pad starts there; checked with simulated keys). - **The mod's own menus are a `.menu` file.** The three buttons the mod adds under Mission Select (Two players online, Join, Split screen) and the rows of its popups (games found, host, saves) were arrays of strings in `menus.c`; they are `mw2coop/menus.menu` now, in the Call of Duty `.menu` syntax other mods use (`menuDef`, `itemDef`, `name`, `text`, `title`, `action { play "mouse_click"; exec "..."; }`; the subset the mod reads, documented at the top of the file). A copy of the file is compiled in (`tools/gen_menus.py`, `--check`), `tools/test_menutable.sh` tests the reader. - **Settings reference.** `docs/settings-reference.md` lists every `settings.ini` key the mod reads (237: `[native]`, `[display]`, `[console]`, `[network]`, ...) with its default, a description and the source line. It is generated from the code by `tools/gen_settings_reference.py` (`--check` tells when it is out of date); the descriptions come from the shipped `settings.ini`, `tools/settings_notes.txt` and the comments in the code that name the key (18 keys have only a generic line). Most `[native]` keys are switches for testing and measuring, not for players.
- **A game build the mod has not seen: its addresses are looked up by byte signatures (first step; 32-bit and 64-bit).** Until now any other `iw4sp.exe` meant "unknown build: nothing is patched". `mw2coop/addresses-x86.txt` and `addresses-x64.txt` (made by `tools/addrsig.py` from the reference builds) hold byte patterns of the code around each address the mod uses; on a build it does not know, `src/addr.c` searches the running build's code for them (0.1 to 0.4 s) and accepts an address only when two signatures agree (or one long code signature does), or, for a global, when its resolved neighbours moved by the same amount; anything else stays unresolved. Measured: the 32-bit signatures against the 1.0.159 exe of the iw4x client give 215 of the 241 addresses right and none wrong; against a second exe with the official layout (the owner's other install, 33 places patched) 235 of 241 are found, all as they are, and the mod recognised the layout and ran with the known addresses (same hooks as on the official exe, split screen started); the 64-bit signatures find 115 of 120 addresses in the game itself. A build whose addresses moved is still not run: the mod's code has to go through the resolved addresses first, and a feature must be switched off when one of its addresses is missing. See `docs/address-resolution.md`.

Checked in the game: a changed help line shows in the console.
- **Split screen frame rate: where the time goes, and a knob (audit 2026-11-09; measured on Roadkill, 1920x1080, bot session, `[native] perflog=1`).** In split screen about a third of every second (333 ms) went into the swaps of the two contexts' state; only about 60 ms of that is copying. The rest is the wait for the render thread at each swap of the per-half sun state (`sunwait`): the main thread and the render thread run one after the other, not side by side. Switching the sun wait off (`sunwait=0`) gave 123 fps instead of 97, switching the per-half sun state off (`sunsplit=0`) 126; all four per-half render states off (`sunsplit`, `viewsplit`, `blursplit`, `fxsplit` = 0) gave less (111), so the other waits are not the cost. The defaults are unchanged: with `sunwait=0` a half can show the other half's sun glare or blind for a moment when someone looks into the sun. The profile of the mod's own code (`loadprof`, 20 s of a split session): about 2.5% of the busy samples; the hottest game code is the vertex unpacking on its worker threads. Two small changes on the way: the HUD layout read `[native] hintdx` from `settings.ini` for every HUD item of every frame (cached now; no change in fps could be measured), and the `viewrun` divisor is read once.
- **Network co-op: a client whose hands are empty gets his weapon key pressed for him (issue 13, "the client loses his weapon without a cause"; the cause itself is not found, the empty hands are put right).** `sync_weapons` sets the dvar `mw2coop_p2_weapnext` when player 2 holds nothing while player 1 holds a weapon, and in split screen the DLL presses the second pad's weapon key; over the network nothing reached the client, who keeps his own weapon choice and undoes a script's `SwitchToWeapon`. Both machines run the script in lockstep and set the dvar, so the client's DLL now runs the weapon binding (`mw2coop_bind weapnext`) on its own machine. Checked with two copies of the game on one PC (bot scenario `weapnexttest` on Oil Rig: the client's player 2 changed from the rifle to the other primary within a second of the press); not seen on two PCs, and the real cause of the loss (a Steam client, once or twice a mission, at door assaults) is still open.
- **32-bit game: a missing entry of the name table no longer crashes the level load (`iw4sp.exe+0xfb41b`).** The client setup of a level load reads a text through a table of pointers indexed by a word of the client state; after a level change inside one session the entry was missing and the read of its first word faulted. In the bot scenario `hop` (Trainer, Roadkill, Cliffhanger) two of two runs crashed in the 32-bit game; with the guard (`guards.c`: a missing entry gives an empty text, logged) four of four runs passed that chain. One longer chain crashed in the NVIDIA driver's own thread (`nvd3dum.dll`), which the mod cannot guard. The iw4x-sp client is not covered.
- **Split screen: a level change inside one session (the mission's end, the next mission) no longer crashes.** Player 2's half (context 1) is seeded from the game's client state once, and the seeding was cleared only when a session began or ended, so after the first level context 1 kept running on the previous level's copy: lists and pointers into memory the level change had freed. Two seconds into the second level the game faulted in the render thread (`iw4sp.exe+0x11b6f6`) or the main thread (`+0x1bdef0`); the v0.6.0 build did it in one of two runs of the bot scenario `hop` (Trainer, then Roadkill). The seeding is now cleared at every level's client init. Checked: eight console `devmap`s of one level in a row over a running split screen game (the same fault, in the animation update, `+0xfcbf6`, hit the third load before), a chain of nine missions in a row (Trainer to Oil Rig) in the 64-bit build and one of four (Cliffhanger to Invasion) in the 32-bit build, no crash, the game's memory flat (1.4-2.4 GB, about 820 handles, no growth over the loads). Not checked with two people; a 32-bit chain Trainer, Roadkill, Cliffhanger still crashed while loading the third level (`+0xfb41b`, see Known issues).
- **Cliffhanger, split screen: the game no longer crashes when the ice axes are handed out (Vlad, 2026-11-08).** The client's loop over entities that are being removed fetches each one's drawing object (DObj) and sets a flag on it. In split screen both halves share the DObj table, so when both remove the same entity the second finds none and the flag write read address 0xf (`iw4sp.exe+0x299ee0`, from the handout's scene). The loop now skips an entity without a DObj, and the flag setter ignores a null object (`guards.c`, under `hotguards`). The bot scenario `climb` crashes at the handout in v0.6.0 at exactly that address and gets past it now.
- **A falling hit with no fall behind it is undone (Vlad: player 2 "hurt himself" on Oil Rig; reproduced in split screen).** His log shows player 2 hovering one unit above the deck for 20 seconds after a restart, then "landing" in the same spot with 100 points of `MOD_FALLING` damage and going down. The engine measures a fall from where the player left the ground and that start was stale. `maps\_mw2coop` now watches each player: a falling hit when the player has lost less than 64 units of height in the last 3 seconds gives the health back (the game needs 140 for any damage), and the stock down check in `maps\_coop::player_coop_proc` ignores the hit (`_coop.gsc.patch` 5), so he is not downed. Reproduced with bots: start `rig` of Oil Rig, `mw2coop_qa failspin` (the mission is failed 12 s in); after the restart player 2 hovers at 1287 716 -1974 with empty hands for 17 s, then lands with 100 `MOD_FALLING` damage and went down; now the log says `falling damage 100 without a fall (1 units) undone` and he stays up with full health. A real fall of 300 units still hurts (bot scenario `falsefall`). The hover itself is probably the level's own water state (the `rig` start is the surfacing: the players swim and wait to be helped out of the water, `player_ready_to_be_helped_from_water`), and the 100 points are the engine measuring his climb out as a fall; Roadkill, with no water, lands in 0.4 s. Not verified.
- **QA and tools: `hop` (a chain of missions in one session), `falsefall`, `tools/leak_watch.ps1` (memory, handles, threads and GDI/USER objects of the game every few seconds into a CSV), build warnings of `crash.c`, `weaponfov.c` and `loadprof.c` removed.** A "HANG (no frame 10 s after the cgame init)" line in a bot run can be the level waiting for the briefing film ("Waiting for the other player"): send `mw2coop_briefskip` (`MW2COOP_MID`).
- **Native entity/render paths: remove recurring work that did not affect the default result.** The weapon-definition guard now keeps validated zone-memory regions until the explicit level-zone / `vid_restart` generation changes, instead of sampling QPC and expiring the regions every millisecond on every entity lookup; cache misses still use `VirtualQuery`. The default `psyaw=1` path now takes the body yaw directly from playerState without also building and scanning an unused 128-sample accumulator history; the history is retained for `psyaw=0` and the brief fallback while player 2's client block is unavailable. Its clock frequency is cached and each history sample takes one QPC read. The per-frame `fovscale` condition now reuses the already-cached `fov` setting instead of reading `settings.ini` every client frame, and the EndScene pending flag uses a relaxed atomic read rather than a locked Interlocked read.
- **Aim-target scan: skip sentient-pointer reads for inactive and non-actor slots.** `aim_targets_update()` still scans the entity count after each server step, but it now checks the two in-use flags and entity type before loading the sentient pointer; the existing health, team, visibility and list-publication logic for actor entities is unchanged.
- **Native frame path: disabled diagnostics no longer do per-frame INI reads or timer queries.** The `scanplace` switch was read through the disk-backed `cfg()` on every cgame draw while off; it now uses the session cache. Server-step, context-copy, worker-wait and DObj-sync timings (`perflog`), plus the stall-watch timestamp and `hitchlog` sampling, are skipped unless their diagnostics are enabled. The `waitmsg` and `sndcount` switches in the message and sound hooks are cached too. Gameplay waits, copies, synchronization and `aim_targets_update()` still run unchanged.
- **D3D9On12 probe: the one-shot check now has a lock-free fast path after completion.** `before_present` calls it per frame; after its first attempt it now returns on a relaxed atomic load, while `InterlockedCompareExchange` still elects exactly one caller to perform the probe.
- **Co-op CPU overhead: the QA session recorder and camera probe are now opt-in.** They were started on every co-op mission; the recorder polls both players' buttons and movement state every 50 ms and writes a detailed trace to `mw2coop.log`, while the camera probe samples player 2 for a diagnostic that is only useful when investigating camera mismatches. They now run only when `set mw2coop_diagnostics 1` is set before loading a mission. Normal gameplay keeps the same co-op logic without those diagnostic threads.
- **D3D9 draw path: Bink detection no longer uses a locked Interlocked read on every indexed draw.** The active flag is now read with a relaxed atomic load; Open/Close still publish it with Interlocked operations. This removes an unnecessary locked read-modify-write from ordinary gameplay while preserving movie fitting.
- **64-bit entity guards: the renderer entity table is no longer revalidated for every entity.** Its pointer is cached per thread while the renderer owner remains unchanged, and the cache is invalidated before each level-zone load and `vid_restart`; a null renderer owner still returns the guarded empty entry. The initial lookup still uses the existing memory check. Weapon-definition and slot-array checks also share one performance-counter sample, while retaining the per-thread 1 ms readable-span cache.
- **Co-op lobby: leaving the campaign lobby lands on the single-player main menu, not on Special Ops (the exit routing, second part).** The first fix watched the UI state and opened `main_text` when the state became `main_specops`; when the game's own "leave" popup (`leave_lobby_warning`) opens `main_specops` by a menu script, the UI state never changes and nothing was routed. While the lobby holds a campaign mission the mod now changes `"main_specops"` to `"main_text"` in that popup's scripts (the native ones come back for a Spec Ops lobby), asks for `main_text` once more if the UI state is still `main_specops` 1.5 s after the first request, and logs the popup's items the first time it sees them, so the next report shows what the game runs.
- **Console: `sv_cheats` is an ordinary changeable dvar, independent of `sv_cheats_default`.** The game registers `sv_cheats` as read-only after the start (INIT/ROM) and the flags were cleared only by the `sv_cheats` command or by `sv_cheats_default=1`, so `set sv_cheats 1` and the dvar list were refused otherwise; and `seta sv_cheats 1` marked it for saving, which would bring cheats back at the next start. The console now takes INIT, ROM and ARCHIVE off the dvar whenever it finds them (value untouched), so it can be changed in every way and is never written to the config.
- **DLSS Super Resolution (experimental, off by default, GeForce RTX only).** `[display] dlss=1` uses NVIDIA's DLSS instead of FSR 3 on the same frame path (Direct3D 12 layer, jitter, depth and motion vectors). NVIDIA's SDK may not go into this open source repository, so the DLSS call lives in a separate `mw2coop_dlss.dll` that you build yourself from `src/dlss` with NVIDIA's SDK (see `src/dlss/README.md`), together with NVIDIA's `nvngx_dlss.dll`; the main `winmm.dll` has no NVIDIA code and the default archives and the GitHub nightly do not carry the bridge. In the game it starts, creates the feature (1280x720 to 1920x1080 and DLAA at 1:1) and evaluates without errors; whether it ghosts while turning is not checked yet, and it gains no FPS at 1080p in this CPU-bound game (measured, see the FSR notes). 64-bit only.
- **The log says which graphics card the game's Direct3D 9 device opens** (`d3dcap: adapter 0 is '...'`), to tell a laptop's integrated card from the GeForce in a report.

- **FSR 3 upscaler on the Direct3D 12 layer (`[display] fsr3=1` with `upscale_width` / `upscale_height`, experimental, off by default; switches `d3d9on12` on).** The game renders at its own size (say 1280x720) and AMD's FSR 3 upscaler (loaded at run time from `fsr3_dir`, the folder with AMD's signed `amd_fidelityfx_loader_dx12.dll` and its upscaler DLL, which the mod does not ship: `third_party/fidelityfx/README.md`) makes the output size (1920x1080) from it (`src/fsr3.c`). It runs in the middle of the game's frame: when the game has finished its 3D picture and is about to start its last pass (the bloom glow and the HUD, which it draws for a full-size back buffer), FSR replaces the 3D picture with the upscaled one, so the bloom lands on the lights, the HUD and the subtitles (with their shadows) are drawn on the upscaled picture at their normal sharpness, and nothing is composed afterwards. The textures of the world pass are sampled with a negative LOD bias (log2(render / output) - 1, as FSR asks), and FSR's own sharpening is on (`fsr3_sharpness`, 0 to 100, default 50, 0 = off). Frames without a 3D view (menus, loading screens, videos) pass through untouched. - **FSR 3: moving characters no longer smear, the depth and the camera given to FSR are the real ones, sharpening 60 (experimental; night work of 2026-11-08).** The camera motion vectors treat every pixel as static world, so a soldier turning his head, or the weapon in your hands, was blended with the wrong place of the previous picture: smear, blocks and "grain" on characters (seen in the Trainer's opening scene). Seen in captures of the Trainer on the RTX 3060 (1280x720 to 1920x1080): the soldiers are clean and sharp with the passes and smeared without them. - **Split screen: the characters around you no longer stutter.** The jerk of every AI actor (the team, the enemies, the civilians), seen in both halves since the split screen began, is fixed. Cause: in single player the game's server and its client share ONE array of the snapshot's entity states, and the server overwrites it at every snapshot build (20 times a second); the client copies the states of a snapshot out of it when it reads that snapshot, and in the split screen that read comes late, after the next build, so it got the newer snapshot's states: one step of the actor's walk was skipped and the next one read twice (a freeze, then a jump). The mod now keeps a copy of that array per build, tagged with the snapshot's time, and the client reads the copy of the snapshot it is reading (`[native] entring=0` turns it off). Measured on No Russian with the actors' per-frame positions: frames in which a walking actor does not move fall from 20-35% to 0-1% in both halves; the server's own movement was regular all along. The same fix is in the 32-bit and the iw4x-sp builds (in the split screen about half of the snapshot reads were late in all three, none in the plain game).
- **Split screen: the AI no longer holds back for player 2's body** (QA finding, not changed in the game): with player 2 ignored by the AI the server's own per-step stalls of an actor fall from 12% to 4%, so part of the unevenness in the split screen comes from the AI reacting to the second player (blocking, waiting). That is how the game's AI behaves with two players and was left alone.
- **Renamed to Modern Warfare 2 Enhanced.** The GitHub repository is now `stxlvn/mw2_enhanced` (the old address redirects). The `mw2coop` folder, the `winmm.dll` proxy, the settings, the dvars and the archive names stay as they are, so installs and saves keep working.
- **Split screen: the names over the players are Alpha and Bravo.** Both halves showed the profile's nickname (player 2's with " (2)" after it). `[native] p1name` and `p2name` in `settings.ini` set other names.
- **Russian game: the Favela Escape objective no longer names Price** (issue #6). The stock text told the player to help Captain Price reach the landing zone before Price has appeared in the story; it now says Captain MacTavish, as in the h2-mod translation. Only the Russian text is replaced.
- **Split screen: the sun's fade now really stays in its own half, in all three builds.** The renderer writes that state while it draws
  the previous frame, after the game had already switched to the other player's view, so each half held the other view's
  value (the 32-bit and iw4x builds did not even have the per-view state in v0.5.7.5-beta, whatever its note said). The swap now waits for the renderer first (`[native] sunwait=0` turns it off;
  `sunsplit=0` turns the per-view state off). Checked on Boneyard with a turning player 1: his half's value follows his view, player 2's stays his own (64-bit, 32-bit and iw4x-sp). The wait costs about 1 ms per frame in the 32-bit build (146 instead of 169 draws a second in a QA run), nothing measurable in 64-bit.
- Diagnostics only (off by default): `sunlog`, `npclog`, `npcwait`, `npcsnap`, `snaplog`; QA scenario `sunlook`.

## v0.5.5-beta (2026-10-29, pre-release of 0.6.0)

A pre-release for people who want to try the split screen and tell us what breaks; the final 0.6.0 follows after more
testing. Everything here was tested with bots on game copies on one PC (and the split screen with frames of both
halves and simulated gamepads); none of it has been played through by two people yet.

### New: native split screen (one game window, one process)

The **Split screen** button of the campaign menu no longer starts a second game; both players are in the one game, the
picture cut top and bottom like the Xbox 360 version: each half has its own view built for its shape (field of view of
the console's split screen), its own weapon, ammo and compass, and text that keeps its proportions. The mission starts
as a normal level in this process, the session ends when you are back in the menus. Pause, the objectives, the
briefing and the console show one full-size picture. Texts that belong to both are shown once: the notices at the top
left (a new objective) in the top half, the subtitles and the mission title lines in the bottom half.

- **Lobby:** a card for each player (call signs Alpha and Bravo, no nicknames); each presses a button on the device he
  will play on (keyboard and mouse, or a gamepad), a choice can be taken back, Start waits for both.
- **Controls:** either player on a gamepad (console layout, XInput) or the keyboard; the second player cannot work the
  game's menus, only pause. Gamepad extras as on the console: aim assist (the turn slows over a target, lock-on while
  moving, the aim-down-the-sight snap), vibration, and the pad's buttons instead of key names in hints.
  Options -> Controls has pages "Gamepad: Alpha" and "Gamepad: Bravo" (look sensitivity, inverted look, aim assist,
  swapped sticks, tactical layout, vibration).
- **Picture:** scopes and red dot sights in both halves; each player sees the other's body, holding the weapon he holds
  and walking where he walks, with his name over it; each half has its own effects (the muzzle flash and smoke of one
  player no longer fill the other's half with a white haze); no dark square around the compass; far NPCs no longer
  jump in the bottom half; no "waiting for the other player" text while a level loads.
- **Builds:** the 64-bit game, the older 32-bit game (archive `-x86`) and, experimental, the iw4x-sp client
  (1.0.159 `iw4sp.exe`, archive `-iw4x`).

How: the game's own two-player machinery runs with two client states swapped per frame; the scene's 2D is drawn into
a layer per half and laid over the squeezed view; the game's 2D placement is made for a half. Details and the research:
`docs/native-splitscreen-plan.md`. Settings under `[native]` in `settings.ini` are for testing (QA only).
Known gaps: the gamepads were tested with simulated gamepads only; one sound listener, no second keyboard (the keyboard
goes to one player); the 32-bit split screen was checked on the Trainer and Cliffhanger only, the iw4x-sp one on the Trainer only.

### Loading screen and briefing of the campaign co-op

The campaign co-op and the split screen now load like single player: the mission's briefing film over the whole picture, the bar at the bottom in the middle. Before, they borrowed Spec Ops'
loading screen (another version of the film with a black panel and the studio logo, the bar at the left, "waiting for the other player"): the Spec Ops lobby they use sets the game's
`specialops` dvar, and the loading screen follows it. The dvar is 0 from the launch to the end of the level; Spec Ops is untouched.

In the online co-op the level used to start the moment both PCs had loaded and cut the briefing off. It now waits for the film, as in single player (the level is paused meanwhile, the film
plays on both PCs); when one player skips the briefing or the film ends on his PC, the other PC lets go at once. (64-bit, 32-bit and iw4x-sp; the split screen has the single player wait already.)
QA runs do not wait (`mw2coop_qa` set; `mw2coop_qa_brief 1` to test the wait).

### Fixed: the Museum, missions in the lobby, a hang

- **Museum for two.** The credits camera carries both players and each sees the museum, not the inside of the other's head (both are hidden from each other during the credits). The museum's civilians play their idles again: the game's animation tables for them were incomplete in the credits mode and the vanilla game raised ten million script errors there (and left civilians in a T-pose), in single player too.
- **All missions can be picked in the co-op lobby** (issue #3): the host sees every mission of the campaign list as open, whatever his save says. Nothing is written to the profile, and his own Mission Select keeps its rules.
- **A rare hang of both PCs after a mission start** (seen once in the 32-bit build): the game's asset database lookup `DB_IsXAssetDefault` did not give back the reader count it took when a name was missing, so the next writer waited for ever. Fixed in both builds.
- **No Russian**: the far ending no longer raises a script error (Makarov's second shot killed the van mate and his idle loop failed; he gets a bullet shield during the shots).
- QA: the checkpoint bots (`cptour`) now run on every campaign mission in 64-bit and 32-bit builds and count the level's own checkpoint remaps.

### Changed: the fonts of the Russian game are the H\*-Mod fonts

The font replacement of v0.5.0-beta now uses the **H\*-Mod fonts** (made by Vlad Loktionov for h2-mod): a Bank Gothic
like face for the headings and the HUD, a Conduit like one for descriptions and subtitles, a bold one for the mission

### The 32-bit game and the iw4x-sp client (archives `-x86` and `-iw4x`)

`mw2coop-v0.5.5-beta-x86.zip` is the build for the older 32-bit MW2, `mw2coop-v0.5.5-beta-iw4x.zip` the one for the

## v0.5.0-beta (2026-10-25)

Everything here was tested with bots on two game copies on one PC (host + client); none of it has been played through
by two people yet.

### New: fonts closer to the English original (Russian game)

The Russian game draws every text in one generic condensed sans, while the English original uses Bank Gothic (headings,
HUD numbers), ITC Conduit (running text) and T26 Carbon (mission intro screens), none of which has Cyrillic. The mod now
renders the game's own font tables again from free fonts with Cyrillic and puts them into the game's memory: **Tektur**
for the headings, the HUD and the mission intro text, **Fira Sans Condensed** for descriptions and subtitles (SIL OFL,
shipped in `mw2coop\fonts`). Works in the 64-bit and the 32-bit build. `fonts=0` under `[display]` in `settings.ini`
keeps the game's own font; the English game is never touched.

### New: scenes that only the first player had are now for both

These scenes were scripted for one player; the other stood by or was left behind. Each now plays for two, with a
rig of his own where the animation needs one.

- **The Gulag, cellblock rope**: both rappel down, one after the other.
- **The Gulag, the evacuation**: both lie buried, each clips on the Pavelow's rope with his own use key (the
  rope's trigger stays on until both have), both are pulled away. A player who is too late is buried by the
  cave-in, as before.
- **Just Like Old Times, the opening rappel**: whoever hooks up first rappels and kills the guard below; the hook-up
  is free again and the other rappels the same way. The barracks checkpoint waits until both are down (it used to
  pull player 1 up to the top in the middle of his knife kill).
- **Escape from Favela, the big jump over the gap**: whoever leaps (or falls) first starts it; both play the
  jump (Soap reaches for both) and wake up on the ground side by side. Each rig starts 55 units from the other, so
  nobody begins inside a wall or inside the other.
- **Escape from Favela, the chopper's rope ladder**: whoever leaps for the ladder first starts the scene, the other
  catches the same rope. A partner far behind is brought to the rooftop slide, so you reach the ledge together.
  Both screens fade out at the end.
- **The Only Easy Day..., the escape**: both board the little bird, side by side on the bench; it takes off
  when both are on board.
- **Wolverines!, the Humvee at the end**: checked (it was already done): player 2 gets a seat of the parked Humvee.

### Cliffhanger and the other levels, from the playtest and after

- **Cliffhanger**: both players get the level's stealth visibility (player 2 was seen at any distance); the other
  player sees the snowmobile's full third-person model; the rider sits on his snowmobile in his own body (the
  co-op body's mesh on Soap's skeleton, so the AI driving animation fits), hands on the handlebar, upright; on the
  ice climb the partner sees the climber's body, not four arms, and the ice picks stand upright in both hands.
  A swing clicked during the last one counts (the mouse buttons sometimes needed two clicks); this one is a
  guess and easy to revert on its own.
- **S.S.D.D.**: the course's gates close once both players are through; either player's sprint counts.
- **Team Player**: either player can start the seat swap; the passenger starts looking ahead; nobody hurts the
  other during the ride.
- **Lobby**: the password mode has its own Password row, and Start is refused until a password is set.
